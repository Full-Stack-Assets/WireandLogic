Across niche programming circles, from OSDev to the demoscene, a growing chorus is denouncing the use of large language models. Blog posts and Hacker News threads have documented how LLMs are being labeled as cheating and a threat to the craft. When the learning process itself is the reward, delegating code generation can erode the very expertise that sustains these communities. Understanding this resistance helps builders decide when an LLM is a lever versus a shortcut.

<Callout type="takeaway">In hobbyist dev circles, LLMs are seen more as a shortcut that undermines learning than as a productivity boost.</Callout>

## What happened
The original blog post notes that hobby programming groups such as OSDev, LangDev, and the demoscene treat the act of mastering a difficult domain as the primary product. In these circles, code that merely runs is a nice‑to‑have, while the deep understanding behind it is the reward, leading many to view LLM‑generated solutions as missing the point entirely. A recurring theme is gatekeeping: respect is earned through years of shared elegant code and demonstrated curiosity, and LLMs are often cast as a cheating shortcut that bypasses this ritual.

A Hacker News discussion expands on the programmer’s workflow, breaking it into five phases from problem definition to deployment. Participants argue that LLMs excel at the middle step—writing code—but the communities that value the “tinkerer” mindset cherish the hands‑on problem‑solving phases. Even when some developers use LLMs for rapid prototyping, the output frequently sparks disagreement, forcing a back‑and‑forth that can surface better solutions but also highlights the lack of deep domain knowledge in the model.

Comments on Lobsters echo the sentiment, emphasizing that the journey of learning, not the final product, defines these groups. The fear is that reliance on AI tools will erode the craft, turning a deeply human pursuit into a transactional shortcut.

## Why it matters
If the learning loop is short‑circuited, newcomers miss out on the iterative debugging and reasoning that forge expertise, potentially weakening the community’s knowledge base. Projects that depend on surface‑level code risk subtle bugs and security flaws that only seasoned practitioners would catch. Moreover, a split emerges between those who embrace LLMs and those who reject them, threatening collaboration and the open‑source ethos that many hobbyists cherish.

## How to think about it
Treat an LLM as a specialized assistant rather than a replacement for the learning process. Start by defining the problem yourself, then use the model to suggest snippets or alternatives, and always verify the output against the underlying principles of the domain. Document any AI‑generated code, annotate why it was accepted or rejected, and share those insights with the community to keep the collaborative spirit alive. When the goal is mastery, limit the model to the “lever” stage—refining or extending code you already understand.

<Callout type="warning">Do not let an LLM replace the iterative debugging and reasoning that defines mastery in niche domains.</Callout>
