When we launched the first version of our internal web app, users reported that opening the site in multiple tabs sometimes caused authentication to disappear. The affected tab remained stuck until the page was refreshed or closed, breaking the user experience. Investigation traced the failure to a shared frontend authentication library that was trying to refresh a token that had already been invalidated. The root cause turned out to be a race condition between tabs, a subtle bug that spanned both frontend and backend boundaries. Fixing it required coordination across the two teams that own the library and the authentication service.

<Callout type='takeaway'>The bug was a cross‑tab token‑refresh race condition hidden in a shared auth library.</Callout>

## What happened
After the initial release, opening the application in several Chrome tabs occasionally resulted in a 403 Forbidden response when the frontend attempted to refresh the authentication token. The 403 broke the refresh flow, leaving the tab unable to recover without a full reload.

The senior developer collected logs and presented them to the team that maintains the shared authentication library. That team argued the backend service should never return 403 for a refresh request. A second round of investigation with the backend owners revealed that the library was sending a refresh token that had already been invalidated by another tab that had successfully refreshed earlier.

The underlying race condition meant that one tab refreshed the token, invalidated the previous refresh token, and another tab—still using the stale token—received the 403. The fix involved adding a lightweight coordination mechanism (using BroadcastChannel) so that tabs serialize refresh attempts, and updating the backend to tolerate stale refresh tokens for a short grace period.

## Why it matters
Multi‑tab usage is a default pattern for modern web applications; a hidden race condition can silently lock users out, eroding trust and increasing support load. Because the bug lived in a shared library, any team that imported it inherited the problem, magnifying its impact across the organization. Coordinating fixes between separate frontend and backend owners also highlighted the risks of siloed ownership for authentication concerns.

## How to think about it
Treat token refresh as a shared resource when multiple tabs or windows can act on it. Use a browser‑level messaging channel (BroadcastChannel, SharedWorker, or Service Worker) to serialize refresh attempts, or store a single source of truth in sessionStorage and let other tabs listen for updates. Keep refresh tokens short‑lived and design the backend to handle occasional stale tokens gracefully. Finally, embed observability (metrics on refresh failures) to catch similar race conditions early.

<Callout type='warning'>Do not store refresh tokens in localStorage without a coordination strategy; doing so makes them vulnerable to exactly this kind of cross‑tab race condition.</Callout>
